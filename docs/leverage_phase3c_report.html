Decision after_days is reliable — switched Chain B to it

after_days was checked, not assumed: it's a plain, correct calendar-day subtraction, uses the identical naive-IST now reference as the session-based branch, runs through the exact same atomic/checksum-verified/idempotent downgrade machinery, and required zero code changes to retention_service.py or resampler.py — only the policy config's two Chain B entries changed shape.

One precise implementation detail that had to be gotten right: _compute_cutoff checks if rule.after_trading_sessions: first — a populated value there always wins over after_days, even if both are set. So after_trading_sessions had to be fully omitted (not zero, not present) from the 1D→1W and 1W→1M policy entries, not just have after_days added alongside it. This is now a directly tested invariant (test_load_policy asserts Chain B rules have a falsy after_trading_sessions), not just an implementation note.

"2 years" and "5 years" are now exactly 730 and 1825 calendar days — no sessions-per-year approximation, no assumption that every year has exactly 250 trading sessions. This directly satisfies the requirement that these represent calendar-time retention.
