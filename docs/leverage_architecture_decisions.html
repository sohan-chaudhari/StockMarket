Decision 1

§1

Daily-candle source of truth

Current situation

stock_data and candles (timeframe=1D) both hold daily OHLCV for overlapping tickers, populated by completely independent code paths, with inconsistent precedence: the daily endpoint reads stock_data first, while the weekly/monthly endpoints read candles first.

Evidence
stock_data writes: main.py:2899 (yfinance fallback), :2955 (Angel One REST fallback), :3001 (copies FROM candles(1D) as a last resort) candles(1D) writes: backfill_daily.py:99 — a standalone script with no scheduler/cron wiring found in main.py Precedence comment: main.py:3225 "# Prefer aggregated ... from the unified pipeline" (weekly/monthly only — contradicted by the daily endpoint's own precedence, which favors stock_data) Retention config (config/retention_policy.yaml) defines a 4h→1D downsample rule, meaning retention_service.py's generic downgrade path (retention_service.py:244) may ALSO write candles(1D) over time for aged data — this was not conclusively ruled out by either audit pass and should be confirmed before final migration, not assumed either way.
Problem

Two schemas, two population mechanisms, no enforced agreement, and no evidence either was checked for adjusted-vs-unadjusted price consistency. yfinance and Angel One REST do not necessarily apply the same split/dividend-adjustment convention — if stock_data leans on yfinance's typically-adjusted series while candles is fed by Angel One's typically-unadjusted feed, the two tables could disagree by more than rounding error around any corporate action, and nothing in the code currently checks for or corrects this.

Options
Option A — candles canonical Recommended
Pros
One unified schema across every timeframe, sharing the same (ticker,timeframe,timestamp) idempotent-upsert discipline already proven reliable for intraday data. Already the precedence winner for weekly/monthly — adopting it for daily removes the inconsistency rather than deepening it.
Cons
Today's daily depth in candles is thin and only reachable through a manual, unscheduled script — real historical depth currently lives in stock_data.
Risks
A naive cutover before backfilling would visibly shrink daily chart history for users. Needs the adjustment-convention question answered first, or the migration silently bakes in a pricing inconsistency.
Option B — stock_data canonical
Pros
Already the deepest, self-healing daily source in production (triple fallback chain inside the request handler).
Cons
Requires flipping the weekly/monthly precedence instead (more endpoints touched, not fewer), keeps daily data outside the unified timeframe/retention infrastructure permanently, and keeps request-time dependency on external APIs (yfinance/Angel One) inside a user-facing endpoint — a latency pattern already implicated in prior dashboard slowness.
Risks
Locks in two schemas forever rather than converging on one; every future timeframe feature has to special-case daily data.
Option C — Phased transition (the practical form of Option A)
Pros
De-risks Option A: run a one-time diff between the two tables to quantify actual drift, add a scheduled EOD job writing into candles(1D) so it stops depending on a manual script, then cut reads over once verified. stock_data stays as a read-only fallback during the transition window, not deleted.
Cons
More steps than a direct cutover.
Risks
Low — this is the safety valve on Option A, not a separate architecture.
Recommendation
Option A, executed as Option C's phased transition. Adopt candles as the single canonical daily source, but only after (1) a scheduled EOD job replaces the manual backfill script, (2) the adjustment-convention question is answered, and (3) a row-level diff against stock_data is reviewed.
Why

The unified candles table is the only one of the two with proven idempotency discipline across concurrent writers, and it's already where the rest of the timeframe hierarchy lives — keeping daily data outside it is the anomaly, not the norm. The phased approach exists specifically because "already implemented and deep" (Option B's real strength) is a legitimate reason to move carefully, not a reason to keep two permanent sources of truth.

Consequences

/api/stock-data/range and /range/paginated would eventually read from candles instead of stock_data; weekly/monthly endpoints need no change since they already prefer candles. stock_data would move to a deprecated/read-only role during the transition, not be deleted.

Migration impact

Endpoints touched: /api/stock-data/range, /range/paginated. A new scheduled EOD backfill job is required (does not exist today — backfill_daily.py is manual-only). No schema change to either table is required for the transition itself.

Testing required

A row-level diff report (ticker × date, both tables) surfacing any close-price or volume mismatch beyond a defined tolerance, run before cutover. Regression tests on /range, /weekly, /monthly against the post-cutover source. A specific test asserting adjustment-convention consistency around at least one known historical split/dividend event.

Decision owner
Core-team decision — no team-owned system depends on this yet, but Team 2 (Recommendation) should be briefed before final cutover since they will eventually train against whichever table wins.

§2

Canonical live-ingestion resolution

Current situation

5-minute candles are the only timeframe built directly from live ticks and persisted; 15m/30m/1h/4h are derived in memory from completed 5m candles; historical tiers above that are produced by checkpointed downsampling, never independently re-aggregated from raw ticks.

Evidence
aggregator.py — Live5mBuilder is structured specifically around a 5-minute bucket concept, not a generic N-minute one live_timeframe_manager.py — consumes candle.5m.completed events only; nothing in the live path currently produces or persists 1-minute bars No Angel One interval-limit figures were found cited directly in historical_service.py during either audit pass — the general SmartAPI convention that finer intervals carry shorter maximum REST lookback windows than coarser ones is treated here as an industry-standard ASSUMPTION requiring verification against this repo's actual chunking logic before being relied on
Problem

Nothing in the current codebase demonstrates a need for sub-5-minute resolution — but the choice is a one-way door: historical data stored only at 5-minute resolution can never be reconstructed to 1-minute resolution later, and a broker's own historical retention for fine intervals is typically time-limited, so even a late REST backfill may not be able to recover it. If Options Intelligence turns out to need tighter entry/exit precision, the cost of not deciding this now is permanent, not just delayed.

Options
Option A — Keep 5-minute canonical (status quo) Recommended, conditionally
Pros
Most mature, tested part of the codebase; 1/5th the storage and write pressure of 1-minute; matches every demonstrated consumer today (no options/recommendation code exists to require finer).
Cons
Forecloses 1-minute (or finer) backtesting for any date before a future switch, permanently.
Risks
If Team 1 later needs finer data, every day that passes under this decision is unrecoverable history.
Option B — Switch to 1-minute canonical
Pros
Removes the one-way-door risk entirely; every higher timeframe becomes a pure, uniform aggregation of one source.
Cons
~5x storage/write volume on the exact tier that's already shown DB-write pressure and soft-cap issues (§5 below); requires rewriting Live5mBuilder's bucket-specific structure; more REST chunking calls during recovery/backfill, worsening the recovery-storm risk already identified.
Risks
Stacks a canonical-resolution rewrite on top of existing, unresolved reliability gaps (dedup, calendar, cap) — the highest-risk option of the three, on a codebase not yet hardened enough to absorb it safely.
Option C — Dual canonical (1m and 5m both persisted)
Pros
Keeps the current 5m infrastructure's stability while adding true 1m depth going forward; avoids the one-way-door problem from this point on.
Cons
Second live-persistence tier to build, test, and operate; less invasive than full Option B only if 5m is derived from 1m rather than independently tick-built (avoids re-solving the same bucket logic twice).
Risks
Moderate engineering cost; still doesn't recover history before the switch date.
Recommendation
Keep 5-minute as canonical today — do not rewrite the aggregator speculatively. But treat this as a time-boxed decision, not a closed one: get an explicit answer from Team Member 1 on whether Options Intelligence has a firm sub-5-minute requirement before their build starts. If yes, adopt Option C (dual canonical) starting from that decision point, accepting the historical gap before it rather than a disruptive later retrofit.
Why

Rewriting mature, tested infrastructure to satisfy a hypothetical requirement — when no code today demonstrates the need — trades a working system for speculative complexity, which runs against the platform's own stated preference for a modular monolith over premature infrastructure. But because the cost of waiting too long is irreversible, the right move is to ask the question now rather than assume the answer either way.

Consequences

If kept at 5m: Core proceeds with hardening (Decisions 3–6) instead of a resolution rewrite. If Team 1 confirms a 1m requirement: Core adds a second ingestion tier from that point forward; data before that date remains 5m-only permanently.

Migration impact

None today. If later adopted: a new Live1mBuilder (or generalized N-minute builder), a new retention tier definition, and 1-minute REST fetch support in recovery_service.py — all additive, no change required to the existing 5m path.

Testing required

If adopted later: parity tests proving a 5m candle built by aggregating six 1m candles exactly matches one built directly from ticks; backfill-chunking tests against Angel One's actual documented interval-specific range limits (to be confirmed, not assumed).

Decision owner
Joint decision — Core proposes and maintains the default; the deciding input on whether to move to Option C belongs to Team Member 1 (Options Intelligence), since they are the plausible source of a genuine sub-5-minute requirement. Team Member 2 should be asked but is unlikely to need finer than 5m for typical signal generation.

§3

Duplicate-tick / volume double-count handling

Current situation

The live aggregator rejects a tick only if its exchange timestamp is strictly older than the last processed tick for that ticker; a tick with the same timestamp as the last one is accepted and its quantity is added to the forming candle's volume.

Evidence
aggregator.py:225-230 — guard is `tick_ts < last_ts` only aggregator.py:274 — `forming["volume"] += volume` runs unconditionally for any accepted tick angelone_service.py:292 — tick_volume is `last_traded_quantity`, a per-trade delta (correctly not derived from the cumulative day-volume field), which is exactly why an accepted duplicate adds real, wrong quantity rather than a harmless re-diff of zero
Problem

Duplicate/replayed ticks — most plausible during a WebSocket reconnect, where a resubscribe snapshot can redeliver the most recent trade — are not filtered before their quantity is accumulated. Open/high/low/close are self-correcting (same price re-applied is harmless), but volume is additive and has no such protection.

Traced flow

  1. WS drops, watchdog (main.py:4389-4423) detects it, forces reconnect.
  2. On reconnect, subscribed tokens are resubscribed from a snapshot (angelone_service.py on_open) — this is the highest-risk moment for a replayed tick.
  3. A replayed tick carrying the same exchange timestamp, price, and quantity as the last one processed reaches process_tick.
  4. tick_ts == last_ts passes the current guard (only `<` is rejected).
  5. Volume is added a second time for a trade that already happened once.
  6. Recovery (REST-sourced) candles are not vulnerable to this — they come pre-aggregated from the broker, not built tick-by-tick by this app, which narrows the fix's required scope to the live ingestion path only.
Options
Option A — Composite fingerprint dedup at ingestion Recommended
Pros
Dedup happens once, at the point ticks are received (angelone_service.py), before handoff to the aggregator — protects every downstream consumer, not just candle building. Uses a composite key of (exchange_timestamp, price, quantity) since no confirmed globally-unique trade ID exists in the current WS payload fields on record.
Cons
Not cryptographically perfect — two genuinely different trades with identical price+quantity in the same second (plausible in a very liquid stock) would be incorrectly treated as one duplicate.
Risks
The fingerprint cache must survive across a reconnect (not reset when the socket reconnects) or it's blind exactly when needed most — this is an implementation detail that has to be gotten right, not a design flaw.
Option B — True unique trade ID, if the WS payload actually carries one
Pros
If Angel One's SmartWebSocketV2 payload includes a genuine per-trade sequence number or exchange trade ID, this is a strictly better identifier than a composite heuristic — zero false-positive risk.
Cons
Not confirmed present in the fields cited by either audit pass (price, quantity, cumulative day-volume, timestamp only) — needs a direct check of the raw WS payload schema before this can be relied on.
Risks
If no such field exists, this option isn't available and Option A is the fallback by default, not a lesser alternative.
Recommendation
Check the raw Angel One WS payload for a genuine unique trade identifier first (Option B); if none exists, implement Option A — a composite (timestamp, price, quantity) fingerprint cache per ticker, checked and updated in angelone_service.py at ingestion, explicitly surviving reconnects.
Why

Dedup belongs at the point of ingestion, not inside the aggregator's bucket logic — it's a data-quality concern independent of how candles are built, and fixing it once upstream protects any future consumer of raw ticks, not just Live5mBuilder.

Consequences

Volume accuracy improves for any ticker that experiences a WS reconnect during market hours — currently unquantified how often that happens, but the watchdog's existence implies it's not rare.

Migration impact

No schema change. A new in-memory per-ticker fingerprint cache in angelone_service.py, sized and cleared on genuine new-trading-day boundaries. No effect on already-persisted historical volume — this only prevents new double-counts, it does not retroactively correct past ones (a separate, lower-priority data-cleanup question if past inflation is later quantified as significant).

Testing required

A unit test replaying an identical tick twice through the ingestion path and asserting volume is only counted once. An integration-style test simulating a reconnect (fingerprint cache must not reset) followed by a genuine new different trade at the same timestamp (must still be counted).

Decision owner
Core-team decision — fully internal to market-data ingestion.

§4

Special-session / market-calendar authority

Current situation

Two independent implementations of session-boundary logic exist: exchange_calendar.py has real special-session/shortened-session data structures that are never invoked in production, and aggregator.py hardcodes standard 09:15–15:30 hours directly, never importing the calendar module at all. live_timeframe_manager.py separately re-implements the same 09:15 bucket-anchoring a third time.

Evidence
exchange_calendar.py — SessionInfo, add_special_session(), is_shortened_session() defined but only referenced from test_exchange_calendar.py aggregator.py:27-30 — hardcoded NSE_OPEN_HOUR/MIN, NSE_CLOSE_HOUR/MIN constants, no import of exchange_calendar aggregator.py:58-73 vs live_timeframe_manager.py:42-61 — two separate re-implementations of the same 09:15-anchored bucket snap
Problem

A special/shortened session (e.g. Muhurat trading) would build zero candles under the current live path, since the aggregator's hardcoded hours reject any tick outside standard hours regardless of what the (unused) calendar module knows. Three independent implementations of session-boundary logic is also a standing drift risk even on ordinary days.

Options
Option A — Consolidate onto exchange_calendar.py as the single source Recommended
Pros
Eliminates the duplicate-logic drift risk entirely; special/shortened sessions become handled correctly everywhere at once, since every consumer (live aggregator, timeframe manager, resampler, recovery, retention) calls the same function.
Cons
Touches the hottest, most latency-sensitive code path in the app — the per-tick processing loop.
Risks
Refactor risk in the most business-critical module; the shared lookup must be O(1)/cached, not a per-tick DB round-trip, or this trades a correctness fix for a performance regression.
Option B — Leave hardcoded constants, only fix holiday-refresh freshness
Pros
Much smaller, lower-risk change to the hot path.
Cons
Does not fix the actual flaw — special sessions remain silently broken — and leaves the three-way duplicate 09:15-anchor logic in place.
Risks
Low risk, low value — defers the real problem.
Recommendation
Option A. Scope it as a pure extraction refactor — shared, cached calendar lookup functions used by every consumer, with no change to the currently-correct standard-session math — plus a concrete plan for sourcing special-session dates (a manually-maintained list alongside the existing holidays table is an acceptable starting point; the current admin-triggered scrape is not a real automatic source either).
Why

A single source of truth for market calendar logic is a correctness requirement, not a nice-to-have — every other subsystem (recovery, retention, resampling) already implicitly assumes session boundaries are consistent; today they aren't guaranteed to be, just coincidentally aligned.

Consequences

aggregator.py and live_timeframe_manager.py would import calendar lookups instead of hardcoding/re-deriving them.

Migration impact

No new table required — the existing market_sessions table already models a session_type column per the database audit and can carry special/shortened session records without a schema change.

Testing required

Extend test_exchange_calendar.py to cover the aggregator's actual call sites, not just the calendar module in isolation. Add a regression test simulating a known historical Muhurat-trading date and asserting candles are built for it under the new path.

Decision owner
Core-team decision

§5

In-memory timeframe-builder cap

Current situation

LiveTimeframeManager caps concurrent in-memory (ticker, timeframe) builders at MAX_BUILDERS=5000, with LRU eviction restricted to builders that have no active viewer. If eviction finds no candidate, a new builder is created anyway — the cap is soft, not hard.

Evidence
live_timeframe_manager.py:239-240 — MAX_BUILDERS constant and IDLE_TIMEOUT_SEC live_timeframe_manager.py:256-264 — add_viewer calls _evict_lru() then unconditionally creates a builder live_timeframe_manager.py:340-351 — _evict_lru only considers viewer_count == 0 candidates (correctly never evicts an active viewer)
Problem

The cap exists to bound memory growth as users browse many tickers/timeframes through a trading day. It works correctly under normal browsing churn (idle builders get evicted), but fails exactly under the worst-case load: a mass reconnect event (e.g. a backend restart causing every open tab to resubscribe near-simultaneously) spikes active builder count all at once, when almost nothing is evictable because everyone just reconnected and is actively viewing.

Options
Option A — Hard cap, reject new views past the limit
Pros
Simplest possible fix; guarantees a memory ceiling.
Cons
Produces user-facing failures at exactly the worst moment — a reconnect storm, when many legitimate viewers would be turned away.
Risks
Trades an invisible memory-growth bug for a visible availability bug.
Option B — Hard cap with graceful degradation to on-demand resampling Recommended
Pros
When the cap is hit and nothing is evictable, serve the requested (ticker,timeframe) via the existing resampler.py on-demand path — already built, already used for cold/rarely-viewed timeframes — instead of either rejecting the view or growing unbounded. Converts "cap exceeded" into "temporarily slower, still correct."
Cons
Slightly higher latency for the viewer who trips the cap.
Risks
Low — reuses existing, already-tested infrastructure rather than adding a new mechanism.
Option C — Queueing/backpressure
Pros
Smooths load spikes in principle.
Cons
New infrastructure category for a problem that a simpler existing fallback already solves; builder construction is fast/cheap, so queuing delay buys little.
Risks
Over-engineering relative to the platform's current scale and stated preference against unneeded complexity.
Recommendation
Option B — hard cap paired with graceful degradation to the existing on-demand resampler, with the cap-hit condition logged/alerted (currently silent either way).
Why

It closes the unbounded-growth gap without introducing new infrastructure, by reusing a fallback path that already exists for a structurally identical situation (a timeframe that isn't actively hot).

Consequences

Memory stays bounded under a reconnect storm; the tradeoff is visible in latency, not correctness or availability.

Migration impact

add_viewer/_evict_lru in live_timeframe_manager.py need a bounded-creation branch. No schema/data change.

Testing required

A load test simulating a reconnect storm — many simultaneous add_viewer calls past 5000, all with viewer_count > 0 — asserting builder count stays bounded and requests still return correct data via the fallback path.

Decision owner
Core-team decision

§6

Unbounded query path on /api/stock-data/chart

Current situation

GET /api/stock-data/chart accepts a client-supplied limit with no upper bound. When resampling to a higher timeframe, ChartService._build_candles multiplies that limit by up to 60 to size the query against the source 5-minute table.

Evidence
main.py:3297-3299 — `limit: int = Query(5000)`, no `le=` upper bound chart_service.py:94-111,154 — `query_limit = limit * 60` against the 5m table, no pagination/streaming Contrast: main.py:3332,3483 — the sibling paginated endpoints correctly cap at `le=50000` Re-verification finding: no current frontend page or backend caller invokes this endpoint today — it is reachable but unused, so this is a prophylactic fix, not an active incident
Problem

A client (or a future internal caller who doesn't know about this gap) requesting a large limit on a higher timeframe could trigger a single unpaginated query for tens of millions of 5-minute rows — a real OOM/DoS vector, and also a payload size no chart UI would ever usefully render.

Options
Option A — Reuse the existing ceiling already proven elsewhere Recommended
Pros
Cap limit at the same 50,000 ceiling the paginated endpoints already use — a product-informed number already chosen once, not invented fresh. Additionally cap the derived query_limit independently (not just scaling with limit × 60 unbounded) so even a "reasonable" limit for the target timeframe can't explode the source-tier query past a fixed ceiling.
Cons
None significant — this is a narrow, low-risk fix.
Risks
Low.
Option B — Add a maximum date-range constraint instead of/alongside a row limit
Pros
Guards a distinct failure mode — "give me every candle since year zero" — that a row-count cap alone doesn't fully address if combined with a very coarse timeframe.
Cons
Needs a product-informed maximum range (not yet defined) rather than a technical one.
Risks
Low; complements Option A rather than replacing it.
Recommendation
Option A, with Option B added as a second, independent guard once a product-appropriate maximum date range is defined (this itself is a small, separate product question, not an architecture one).
Why

The correct ceiling already exists in the codebase for the sibling endpoints — this isn't a case of picking an arbitrary number, it's applying the number the team already settled on to the one endpoint that was missed.

Consequences

No behavior change for any real caller today (none exist); closes the gap before /api/stock-data/chart is ever wired up to a live page.

Migration impact

None — a bounds check only. Can ship in the same change as the timeframe-case fix, since both live in chart_service.py/its call site.

Testing required

A test asserting a large client-supplied limit is clamped, and that the derived source-tier query never exceeds the fixed ceiling regardless of the requested timeframe's multiplier.

§7 Shared contracts — what Core can safely guarantee

Instrument, Candle, and LivePrice are specified in full. Signal and OptionContract remain UNKNOWN — REQUIRES TEAM DECISION — their internal shape belongs to Team 2 and Team 1 respectively; Core's job is only to state what it can guarantee to whoever eventually defines them.

Instrument

Core guarantees
A stable (ticker, exchange) identity backed by stock_metadata, with instrument_token, name, segment, is_active.
Core does not guarantee
Continuity across a corporate-action re-tokenization — no such handling exists in the code today; treat instrument identity as stable only within a single listing lifetime until this gap is closed.
Timestamp
last_updated on the metadata record.
Mutability
Metadata mutable; identity fields immutable once created.
Backing
Database-backed, should be exposed via a read API rather than direct table access.

Candle

Core guarantees
OHLCV per (ticker, timeframe, timestamp), unique-constrained, upserted idempotently. Timestamps are IST-naive, snapped to the 09:15 NSE session anchor.
Core does not guarantee
That a row is final while is_completed=False — forming candles are mutable. Any consumer building features or training a model must filter to is_completed=True or risk using a value that later changed. Also does not yet guarantee protection against the volume double-count in Decision 3 until that fix ships, nor correct candles during a special session until Decision 4 ships.
Timestamp
Bucket start time — never assume midnight-anchored buckets (the dead v002 materialized-view migration got exactly this wrong).
Backing
Database-backed; recommend an API layer in front of it so the schema can evolve without breaking either team.

LivePrice

Core guarantees
Latest tick/quote snapshot per ticker via /api/live-prices and the WebSocket channels.
Core does not guarantee
Persistence or revision history — this is deliberately not a database-backed contract. It must never be used as historical/training data; that is exactly what the Candle contract exists for.
Timestamp
Must distinguish exchange tick time from server-received time — currently conflated in places in the live pipeline; a consumer needing precise latency measurement should not assume these are the same clock without verifying.
Backing
Event/API only, not a table.

Signal UNKNOWN — Team 2

Core's only guarantee here is a discipline the eventual contract must follow, not its content: whatever generated_at timestamp Team 2 attaches to a signal, Core commits to making Candle data queryable strictly as of that timestamp, so their backtests can enforce point-in-time correctness. The payload itself — score, horizon, model semantics — is entirely Team 2's to define.

OptionContract UNKNOWN — Team 1

Core's only current guarantee is the underlying equity/index Instrument and Candle/LivePrice feed. Core does not yet support option-instrument WebSocket subscriptions — angelone_service.py's token resolution is equity/index-focused today. This is a concrete, named gap Team 1 will hit immediately, not a hidden one — it needs a joint scoping conversation before Team 1's build starts, not a Core-invented schema.
