01 Scope & ownership

This pass covers everything Core Platform is responsible for: market-data ingestion, the candle/timeframe engine, historical data, retention/materialization, recovery, migrations, PostgreSQL, the FastAPI/API layer, frontend chart integration, authentication, security, observability, performance, testing, and deployment. It does not redesign Options Intelligence or Recommendation Intelligence — those are team-owned systems whose internals are out of scope here. Where this report touches them at all, it is only to define the integration boundary: what Core must hand them, and what they must hand back.

Neither system has any code in this repository — confirmed by repeated repo-wide search in both the original discovery pass and this refinement pass. They are represented below strictly as future, team-owned, integration-boundary-only nodes, never as if they already exist.

05 Candle architecture review

Re-examined adversarially across ten specific failure modes, per your request, rather than accepted on the strength of the retention/resampling logic alone.

AreaVerdictEvidence
Holiday handlingFlawHoliday list is DB-driven with a manual admin-triggered refresh only — no automatic sync. An unscheduled/missed holiday silently lets ticks aggregate into real candles. aggregator.py:45-50
Partial / special sessions (e.g. Muhurat trading)FlawTwo disconnected calendar implementations. exchange_calendar.py has real special-session scaffolding (add_special_session()) that is never called in production. The live aggregator hardcodes 09:15–15:30 independently and never imports the calendar module at all — a special session would build zero candles. aggregator.py:27-30, confirmed no import of exchange_calendar
Missing candles / mid-session gapsFlawFully-missing buckets are handled correctly (no row, resampler drops empty bins). But a candle only finalizes when a new tick arrives in a different bucket — an illiquid ticker or WS outage with no further ticks leaves a forming candle that never persists as completed. aggregator.py:260-262, 316-340
Duplicate ticksFlawDedup only rejects tick_ts < last_ts, not tick_ts == last_ts. A reconnect replaying the last trade at the same exchange timestamp is not rejected and its volume is added again. aggregator.py:225-230, 274
Recovery/live overlapFlawRecovery-fetched REST candles default is_completed=True even when the range includes the still-forming current bucket, with no explicit "recovery only touches closed buckets" boundary. recovery_service.py:74-79,106-164, aggregator.py:584,598
Historical/live chart boundarySoundDedup-by-timestamp merge in chart_service.py:63-73 produces a clean seam — verified by code, not by a running system.
Resampling math at session-end edge bucketsSound09:15-anchored offset correctly produces a legitimately shorter final bucket at 15:30, not corrupted data. resampler.py:69-81
Volume aggregation across tiersSound, inherits flawSums correctly across tiers, but any volume inflated by the duplicate-tick issue above propagates unchanged through every higher timeframe — retention's checksum only verifies internal consistency, not ground truth.
Concurrent viewers / memory growthFlawMAX_BUILDERS=5000 is soft, not hard: eviction correctly never touches active viewers, but if none are evictable, new builders are created past the cap with no bound. Plausible under a market-hours traffic spike. live_timeframe_manager.py:256-264,340-351
Large historical range requestsFlaw/api/stock-data/range/paginated and /intraday/paginated correctly cap at 50,000 rows — but /api/stock-data/chart has no upper bound on limit, and resampling multiplies the source query by up to 60x, creating an unpaginated, unbounded query against the 5m table. main.py:3297-3299, chart_service.py:94-111,154
Revised verdict: the hybrid shape — 5-minute canonical from ticks, in-memory derivation of higher intraday timeframes, checkpointed/checksum-verified historical downsampling — is the right shape and should be kept. But "fundamentally sound" was too generous a conclusion the first time: it reviewed the well-tested retention and resampling logic without stress-testing the seams. Four of the ten areas above are concrete, code-verifiable flaws, not theoretical edge cases, and should be treated as real defects to schedule, not merely noted.

08 Hidden risks

  • V /register leaks account existence via a distinguishable 400 response for an already-registered email, before password-format validation runs. auth_router.py:26-27
  • V /resend-verification leaks verified-vs-unverified status through two different response messages for the two cases. auth_router.py:144-149
  • I /forgot-password's uniform response message may still leak via timing (a real send only happens on the existing-user branch), though this is inferred, not measured. auth_router.py:164-182
  • V No endpoint anywhere in the app is tested at the HTTP layer. All 13 backend test files exercise service classes directly, in-process — none import main.py's app or use TestClient. Breaking a route's decorator, request schema, or wiring would go completely undetected.
  • V No CI/CD exists — no .github/workflows/, no Dockerfile for this app (only for the sibling News_Sentiment service), no automated migration runner (no Alembic; migrations are hand-run psql/a manual script).
  • V A hardcoded fallback DB password is present in a maintenance script — run_sql_migration.py's DB_PASSWORD = os.getenv("DB_PASSWORD", "medikart@3145") — this defaults to a real-looking credential if the env var is ever unset, in a script that runs arbitrary SQL against the database.
  • V No environment-tier separation (dev/staging/prod) anywhere in config — one flat .env, no feature flags, no ENVIRONMENT variable read anywhere.
  • V /api/health is not wired to any deployment tooling — it exists but nothing (no Docker healthcheck, no probe, because none of that infra exists) actually consumes it.

10 Shared contracts

The principle: team-owned intelligence systems should depend on a stable contract, never on Core's internal tables or implementation details. Only the contracts with a concrete, evidenced need are designed below in full — the rest are flagged for a joint decision rather than invented.

Instrument

Purpose
One stable identity per tradable symbol, so "RELIANCE" means the same thing to every system.
Owner
Core
Producer
Core — backed by the existing stock_metadata table + Angel One instrument-master sync
Consumers
Recommendation, Options, Frontend
Required fields
ticker, exchange, instrument_token, name, segment, is_active
Timestamps
last_updated — when the instrument master was last refreshed
Versioning
Identity fields immutable once created; corporate-action re-tokenization is not handled anywhere in the current code — a relisting/token change today is a silent break, not a versioned event. Needs a superseded_by pointer before either team relies on token stability long-term.
Validation
(ticker, exchange) unique; instrument_token unique among active instruments
Mutability
Metadata mutable, identity immutable
Backing
Database-backed, exposed through a read API rather than direct table access

Candle

Purpose
Canonical OHLCV bar per ticker+timeframe+timestamp — the one thing every downstream system trains or triggers on.
Owner
Core
Producer
Live aggregator (real-time), retention service (historical tiers), recovery/backfill
Consumers
Frontend, Recommendation (feature generation), Options (underlying price history)
Required fields
ticker, timeframe, timestamp, open, high, low, close, volume, is_completed, data_source
Timestamps
Bucket start time, IST-naive, snapped to the 09:15 NSE session anchor — must be documented explicitly to every consumer; the dead v002 migration shows exactly what goes wrong when a consumer assumes midnight-anchored buckets instead.
Versioning
A row is mutable while forming and should be treated as immutable once is_completed=True — not currently enforced at the DB level. Any model training pipeline must filter to is_completed=True or risk training on values that later changed — a direct data-leakage vector today.
Validation
Standard OHLC bounds; unique (ticker, timeframe, timestamp)
Mutability
Mutable until completed, then immutable (by convention, not yet by constraint)
Backing
Database-backed; recommend an API layer in front of it so Core can evolve the schema without breaking either team

Purpose
Latest tick/quote snapshot for real-time display and fast decision paths.
Owner
Core
Producer

Consumers

ticker, ltp, tick_timestamp, day_open, day_high, day_low, day_volume

Must distinguish exchange tick time from server-received time explicitly — currently conflated in places in the live pipeline.

Signal UNK — shape needs Team 2

Owner

Consumers

12 AI/ML readiness

Not building the AI system — only assessing whether Core's current data foundation could support one without a rework.

DimensionStatusEvidence
Point-in-time correctnessGapForming candles are mutable and not distinguished from completed ones at the DB-constraint level; a naive training query without an explicit is_completed=True filter would leak future information.
Data leakage risk (daily data)GapTwo divergent daily sources (§7) means a model trained against one and served against the other learns and predicts on different numbers.
Timestamp correctnessReadyConsistently IST-naive, session-anchored — a real strength, as long as it's documented in the Candle contract (§10) rather than assumed.
Historical consistency across timeframesGapRetention's checksum verifies internal consistency (source sum = target sum) but not ground truth — the duplicate-tick volume flaw (§5) would pass that check while still being wrong.
Reproducibility of features/signalsGapNo versioning concept exists yet anywhere in the codebase — the proposed Signal.model_version field (§10) is a new requirement, not something to retrofit later.
Instrument identity stabilityGapNo corporate-action/re-tokenization handling exists — a backtest spanning a relisting event would silently break.
Data versioning / lineageGapNo concept of "what did this table look like as of date X" exists — retention physically deletes and downsamples source rows, which is correct for storage but means a backtest can't reconstruct exactly what 5m data looked like before it was compressed to 15m.

Overall: Core is not yet AI/ML-ready, but the gaps are addressable without a rework — they're additive (versioning fields, a completed-only read path, a single daily source of truth) rather than structural. This should be resolved before Team 2 starts training against real data, not after.

14 Migration roadmap

0

Correctness fixes (no architecture change)

Fix the same-timestamp tick dedup gap. Add a hard cap (reject, don't silently exceed) to MAX_BUILDERS. Add an upper bound to /api/stock-data/chart's limit. Fix the index.js duplicate-fetch guard. These are isolated, low-risk, and don't touch the daily-data question.

1

Daily-data reconciliation

Compare stock_data and candles(1D) for the same tickers to quantify actual drift before choosing a winner. Then declare one authoritative source and migrate reads — this needs a verification step, not a unilateral pick (see §15).

2

Calendar unification

Wire the live aggregator to exchange_calendar.py instead of its own hardcoded constants, so special/partial sessions are handled once, correctly, in one place.

3

Publish the Instrument/Candle/LivePrice contracts

Formalize the read-only API surface described in §10 before either team writes code against internal tables directly.

4

AI/ML foundation

Add is_completed-aware read paths, a versioning convention, and resolve the corporate-action gap — before Team 2 trains against real data.

5

Integration onboarding — only after Team 1/Team 2 scope is known

Extend the WS subscription manager for option tokens if and when Team 1 confirms that requirement. Revisit canonical resolution (§ prior report) only if either team demonstrates a concrete need for finer-than-5m data.

15 Decisions requiring human/team approval

1
Which daily-data table becomes authoritative — stock_data or candles(1D). This changes what every existing endpoint reads and should not be picked without seeing the actual drift between the two first.
2
Whether 5-minute stays canonical, or a finer resolution is needed — this is a one-way door: historical 5m-only data cannot be un-aggregated back to 1-minute resolution later. If Options Intelligence is likely to need sub-5-minute data, that should surface now, not after a year of 5m-only history has accumulated.
3
The exact Signal and OptionContract payload shapes — Core can commit to the timestamp/versioning discipline they must follow, but the business fields are Team 2's and Team 1's to define.
4
Whether Options Intelligence gets its own live option-price integration or extends Core's Angel One subscription manager — a real architecture decision with cost either way, not something to default into.
5
Whether Recommendation/Options end up as modules in this same FastAPI process or separate services — deliberately left open in §13 until team scale/isolation needs are known; should be revisited explicitly when either team starts, not assumed now.
6
Retiring dead code (gap_recovery.py, the TimescaleDB folder, the React scaffold, orphaned TV files, legacy per-timeframe tables) — flagged, not deleted, per the standing instruction not to modify production code in this phase.
