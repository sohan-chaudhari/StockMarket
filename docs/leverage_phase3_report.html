§ Timestamp convention — decision, not a fix

Inspected as instructed: config/timeframe_registry.py, the live candle builder (aggregator.py), historical_service.py, chart_service.py, resampler.py, retention_service.py, and how a charting frontend consumes daily bars.

Recommendation: keep 1D at midnight. Do not change it.

resampler.py:69 explicitly excludes '1D' (and 'W', 'MS') from the 09:15-session-offset logic used for every intraday rule — this reads as a deliberate choice, not an oversight: a daily candle represents one entire trading session and is conventionally keyed by date, not by an intraday clock time, in every OHLCV charting convention (including the lightweight-charts library this app already uses, which accepts daily bars as a plain date rather than a timestamp). Under that reading, "midnight" isn't really a competing time-of-day convention at all — it's the natural zero-information placeholder for "this row represents the whole day," and the true convention question doesn't even apply to 1D/1W/1M the way it applies to intraday tiers.

config/timeframe_registry.py supports this: 1D/1W/1M are typed "session"/"week"/"month", structurally distinct from the "intraday" type that carries a minutes field — the registry itself already treats them as a different kind of thing, not a same-kind-different-anchor thing.

What this means for the earlier finding: Phase 2's report characterized the midnight-vs-09:15 difference as a "convention violation." That framing should be revised — it's a real structural difference (correctly observed), but not a defect. The corrective action is to update the shared Candle contract's documentation to state the 09:15-session-anchoring promise applies to intraday timeframes specifically, and that 1D/1W/1M are date-keyed by design — not to migrate any timestamp data. No migration plan is proposed for this item because no change is recommended.

§ Migration plan — computed precisely, NOT executed

Per the instruction to calculate the required range dynamically rather than assume it, this used the app's own nse_calendar session-counting logic (the same code retention_service.py uses) against the real database state.

holidays loaded from the `holidays` table: 0 rows (the table itself is empty — a separate, already-known data-population gap, not a code gap; the cutoff below is therefore a weekday-only approximation, accurate to within a small number of actual NSE holidays) latest 1D candle date (today's anchor): 2026-08-10 180-trading-session cutoff from that anchor: 2025-12-01 → required 1D coverage window: 2025-12-01 → 2026-08-10 (181 sessions) stock_data coverage in that window: 2025-12-01 → 2026-07-10 (covers the older ~85% of the window) candles(1D) coverage in that window: 2026-07-21 → 2026-08-10 (covers the newest ~12%) GAP — covered by neither source: 2026-07-11 → 2026-07-20 → actual trading sessions in that gap: 2026-07-13, 14, 15, 16, 17, 20 (6 sessions, weekday-only estimate)

Proposed 9-step execution (from the prompt's own workflow, with concrete numbers)

  1. Inspect candles 1D coverage — done above (2,643 tickers, 2026-07-21→2026-08-10).
  2. Inspect migrated stock_data coverage — done above; scope to the 2,638 common + 57 active-only = 2,695 tickers, restricted to rows dated 2025-12-01→2026-07-10, excluding the one known-bad NaN row (COALINDIA, 2026-06-02) and any other row failing the OHLCV validity checks in item #12 (high≥low, high≥open, high≥close, low≤open, low≤close, volume≥0, all four price fields finite).
  3. Identify missing ranges — done above: exactly 6 trading sessions (2026-07-13 → 2026-07-20) are covered by neither source, for whichever of the 2,695 tickers don't already have those specific dates.
  4. Migrate valid stock_data rows — INSERT ... ON CONFLICT (ticker, timeframe, timestamp) DO NOTHING using the existing uix_candle_key constraint (the same idempotency pattern retention_service.py and batch_flush_candles already use) — safe to re-run, a second run inserts zero additional rows.
  5. Fetch only the missing 6-session range from Angel One — via historical_service.py's existing getCandleData path, scoped per-ticker to just that window, not a full re-download.
  6. Normalize timestamps — midnight-anchored, consistent with the §Timestamp convention decision above (no conversion needed, this is already candles' native 1D convention).
  7. Validate OHLCV — reject (log, don't insert) any row failing the item #12 checks; explicitly guard against NaN (Python's math.isnan(), since Postgres stores IEEE NaN as a valid float distinct from NULL — confirmed this is exactly how the one known-bad row is stored).
  8. Insert/upsert into candles — same idempotent upsert as step 4.
  9. Verify continuity and duplicates — post-migration query confirming, per ticker, zero gaps in the 181-session window and zero duplicate (ticker, timestamp) pairs (the unique constraint makes true duplicates structurally impossible, but a verification pass would still confirm row counts match expected session counts).
Why this wasn't executed: steps 4 and 5 are real, non-trivial actions — step 4 writes ~2,695 tickers × up to 181 daily rows (up to ~488,000 rows, though the true count is lower since candles already holds the newest 21 sessions) directly into the production candles table, and step 5 makes real calls against Angel One's historical API (subject to their rate limits, and a broker API call is not something to run speculatively). Both are reversible in principle (the rows could be deleted) but not something to execute without an explicit go-ahead, consistent with every other data-affecting step in this engagement.
