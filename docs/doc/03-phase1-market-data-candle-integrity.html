Critical

Holiday calendar desync between execution logic and the aggregator

Issue

Discovered during Phase 1 tracing, not in the original decision package: nse_calendar — the calendar object execution_engine.py, trade_service.py, price_provider.py, and retention_service.py all call for real trading-hours decisions — had an empty holiday set at all times.

Root cause

A separate module-level set, NSE_HOLIDAYS in main.py, is correctly loaded from the DB at startup and passed to candle_aggregator.set_holidays() — but nothing ever called nse_calendar.load_holidays(). NSECalendar.is_trading_day() only checks weekday when its holiday set is empty, so on a real NSE holiday it would have returned True.

Evidence
Verified: grep across the entire backend for `load_holidays(` found zero call sites before this fix. main.py (startup, ~line 4260-4272): NSE_HOLIDAYS loaded from models.Holiday, passed to candle_aggregator.set_holidays(NSE_HOLIDAYS) only. Consumers of the never-fed nse_calendar: execution_engine.py:52, price_provider.py:271, trade_service.py (3 call sites).
Change

Added nse_calendar.load_holidays(NSE_HOLIDAYS) immediately after candle_aggregator.set_holidays(NSE_HOLIDAYS), at both the startup loader and the admin holiday-refresh endpoint in main.py — NSE_HOLIDAYS is now the single set feeding both consumers.

Tests

Not independently unit-testable without a running DB session (this is a wiring fix at a startup call site, not a pure function) — verified instead by (1) reading every consumer's call path to confirm they all resolve to the same nse_calendar singleton import, and (2) the full backend suite (230 tests, including test_exchange_calendar.py's existing load_holidays coverage) passing unchanged.

Result
Execution/trade/retention logic and candle aggregation now agree on which dates are trading days — closing a real, verified correctness gap that existed before any of the six approved decisions were written.
Remaining risk
None identified for this specific fix. It is purely additive (populates a previously-empty set with data already trusted elsewhere) and cannot make any check less correct.

Decision 3 — duplicate-tick volume double-count

Issue

A tick sharing the exact same exchange timestamp as the previously processed tick for a ticker was accepted and its quantity added to the forming candle's volume a second time.

Root cause

aggregator.py's only dedup guard rejected tick_ts < last_ts; a same-timestamp replay (most plausible on a WS reconnect resubscribe snapshot) passed through and forming["volume"] += volume ran again.

Evidence
angelone_service.py _handle_ws_tick: confirmed the WS "Quote" mode payload carries no unique per-trade ID — only token, ltp, exchange_timestamp, day OHLC, day volume, last_traded_quantity. aggregator.py process_tick (pre-fix): guard was `if last_ts is not None and tick_ts < last_ts: ... return {}` — no `==` case.
Change

Per Decision 3's Option A (no true trade ID available → composite fingerprint): added a per-ticker (exchange_ts, price, quantity) fingerprint cache on the AngelOneService singleton, checked in _handle_ws_tick before the tick is forwarded via on_tick_callback — so a duplicate never reaches the aggregator at all. The cache lives on the singleton (not the socket object), so it survives a reconnect intact. Documented limitation directly in code: two genuinely different trades sharing timestamp+price+quantity in the same second would be misclassified as a duplicate — accepted as a smaller, one-sided error than the current double-count.

Tests

tests/test_angelone_tick_dedup.py (new, 6 tests): first tick forwarded, exact replay swallowed, replay-into-aggregator does not double volume (end-to-end through process_tick), a genuinely new tick after a duplicate is still forwarded, same-timestamp-different-price is not treated as duplicate, fingerprint state survives a simulated reconnect.

Result
All 6 new tests pass; full 230-test suite passes. Volume accuracy is protected for any ticker experiencing a WS reconnect during market hours.
Remaining risk
The fingerprint dict is read/written without a lock; if the broker SDK ever invokes _handle_ws_tick concurrently from multiple threads (not confirmed either way — existing code already assumes single-threaded delivery, per the unlocked pattern already used for other per-tick state), a race could let a duplicate slip through. This is no worse than the pre-fix status quo, not a new risk introduced. Does not retroactively correct any volume already inflated by this bug before the fix shipped — a separate, lower-priority data-cleanup question if past inflation is later quantified as material.

Decision 4 — special/shortened sessions build zero candles

Issue

A special session (e.g. Muhurat trading) outside the standard 09:15-15:30 window would have every tick rejected by the live aggregator, building no candles at all for that session.

Root cause

exchange_calendar.py has real special-session data structures (SessionInfo, add_special_session()) but aggregator.py never imported or consulted them — it hardcoded standard hours as module constants, checked in is_market_hour()/snap_to_nse_session().

Evidence
aggregator.py (pre-fix): NSE_OPEN_HOUR/MIN, NSE_CLOSE_HOUR/MIN constants, is_market_hour(dt) with no per-date override, no import of exchange_calendar anywhere in the file. exchange_calendar.py: add_special_session() referenced only from test_exchange_calendar.py before this fix — never called by production code.
Change

Scoped deliberately smaller than a full calendar-implementation merge (the decision package flagged that as the higher-risk path — touching the hottest tick-processing loop). Instead: is_market_hour() and snap_to_nse_session() now accept optional per-date bound overrides (default args reproduce the exact standard-day behavior — zero change for the 99.6%+ of days with no special session). Live5mBuilder gained set_special_sessions() and a _session_bounds(date) lookup, consulted at every point process_tick gates, buckets, or flushes a tick. exchange_calendar.py gained special_sessions_as_bounds() to export its data in the seconds-of-day shape the hot path already works in. Wired at both holiday-load call sites in main.py so nse_calendar stays the single place special-session data is entered, even though nothing populates it yet (no source for real Muhurat-style dates exists in the repo — invented dates were deliberately not fabricated).

Tests

tests/test_5m_builder.py (8 new tests): standard-day behavior provably unaffected by the new optional parameters (exact bucket assertions unchanged), a tick outside standard hours is rejected with no special session registered, the identical tick is accepted and builds a candle once a special session is registered, bounds default correctly when no override exists. tests/test_exchange_calendar.py (2 new tests): the export helper returns the right seconds-of-day tuple for a Muhurat-style window.

Result
10 new tests pass; full 230-test suite passes, including every pre-existing standard-day aggregator assertion, unchanged.
Remaining risk
NOT VERIFIED: live_timeframe_manager.py's _snap_to_nse_bucket is a third, independent re-implementation of the 09:15 anchor and was not updated to consult special sessions in this pass — if a special session ever ships real dates, 15m/30m/1h live views during that session would still misalign even though the underlying 5m candles are now correct. Deliberately deferred rather than rushed: the decision package specifically warned this second consolidation is higher-risk, and fixing it isn't required to close the actual verified bug (zero candles built), only to perfect a currently-inert, data-free code path. No holiday/special-session data source beyond the manual admin scrape exists yet — the plumbing is ready but nothing feeds it.

Decision 5 — soft builder cap allowed unbounded growth

Issue

LiveTimeframeManager.add_viewer() would create a new in-memory (ticker, timeframe) builder even past MAX_BUILDERS=5000 if eviction found no candidate — the "upper bound" the module's own docstring claimed wasn't actually enforced.

Root cause

_evict_lru() only considers builders with viewer_count == 0 (correct — it must never evict an active viewer), but the caller proceeded to construct a new builder unconditionally regardless of whether eviction succeeded.

Evidence
live_timeframe_manager.py add_viewer (pre-fix): `if total >= self.MAX_BUILDERS: self._evict_lru()` followed unconditionally by builder creation, no re-check of total after eviction. main.py:3348 and :3467 (call sites): get_current() already returns None for a missing builder and every caller already treats that as "no live data, use DB/resample" — the graceful-degradation path Decision 5 called for already existed and only needed the cap to actually stop creating builders past it.
Change

add_viewer() now returns a bool, re-checks the total after eviction, and declines to create a builder (returning False, incrementing a new _cap_hits counter, logging the event) when nothing was evictable. No new fallback mechanism was built — the existing DB/on-the-fly-resample path in main.py's paginated intraday endpoint already activates correctly whenever get_current() returns None, which is exactly what happens now instead of the cap being silently exceeded.

Tests

tests/test_live_timeframe_manager.py (6 new tests): success case returns True, unknown timeframe returns False, a second viewer of an already-tracked (ticker, tf) succeeds even exactly at capacity, a genuinely new (ticker, tf) is declined and _cap_hits increments when nothing is evictable, an idle builder is correctly evicted to make room before declining, and get_current() returns None for the declined case — proving the graceful-degradation contract end-to-end.

Result
All 6 new tests pass; full 230-test suite passes. Memory is now bounded even under a reconnect storm that spikes active-viewer count past 5000 simultaneously.
Remaining risk
The viewer whose request trips the cap gets slower (DB/resample) data instead of the live in-memory forming candle, until a slot frees up — a deliberate, documented trade-off per Decision 5, not a defect. _cap_hits is tracked in get_stats() but not yet wired into /api/health or any alerting — an observability follow-up, not required for correctness.
