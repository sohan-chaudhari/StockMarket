Section A

Batch-Boundary Corruption — Bug Proof

Root Cause
retention_service.py · _process_ticker() fetches a fixed-size batch of source rows and immediately resamples the entire batch. With batch_size=100 for the 5m→15m rule, row index 99 (0-based) is always the first slot of a new 15m bucket. The resampler produces a partial target candle. ON CONFLICT DO NOTHING then permanently blocks the correct complete candle when the remaining two slots arrive in the next batch.

The corruption is deterministic, not probabilistic. Every single 100-row batch for 5m→15m triggers it:

arithmetic proof confirmed bug
# slots per 15m bucket from 5m source rows slots_per_bucket = 15 // 5 # = 3 # position of the last row in a batch_size=100 batch (0-indexed) last_row_index = 100 - 1 # = 99 # position of last row within its 15m bucket slot_position = last_row_index % slots_per_bucket # = 99 % 3 = 0 # slot_position == 0 → row 99 is ALWAYS the FIRST slot of a new bucket # two remaining slots (positions 1 and 2) are left for the next batch

This produces the following corruption on every batch iteration:

Field Batch 1 result (1 of 3 rows) Correct result (all 3 rows) Error
open 100 ✓ 100 —
high 112 (only row 0) 125 (max of rows 0–2) WRONG
low 88 (only row 0) 88 (coincidentally same) —
close 105 (row 0's close) 120 (row 2's close) WRONG
volume 1 000 (1 row only) 3 000 (sum of 3 rows) WRONG — ⅓ of correct
Permanent Data Corruption
The partial and complete batches both produce a target candle with the same timestamp (e.g. 09:15 15m). The first (partial) insert succeeds. When the complete version arrives in batch 2, ON CONFLICT DO NOTHING silently discards it. The slot is permanently poisoned with wrong H, C, and volume. There is no self-correcting path without explicit repair.

The bug is latent in the 15m→30m, 30m→1h, and 1h→4h chains too, but does not trigger with batch_size=100 because those multipliers evenly divide 99: 99 % 2 == 1 and 99 % 4 == 3 — both land on the last slot of their target bucket. The fix hardens all chains regardless, so it is safe against future batch_size changes.

Addition 1 — _target_bucket_tail() static method (added before _process_ticker):

retention_service.py — new static method added
@staticmethod def _target_bucket_tail(ts: datetime, source_tf: str, target_tf: str) -> Optional[datetime]: """Return the timestamp of the last source slot in ts's target bucket. NSE session opens at 09:15; all intraday bucket boundaries are anchored to that. Returns None for calendar-based chains (1D/1W/1M source or target) where session alignment does not apply. """ src_minutes = {"5m": 5, "15m": 15, "30m": 30, "1h": 60}.get(source_tf) tgt_minutes = {"15m": 15, "30m": 30, "1h": 60, "4h": 240}.get(target_tf) if src_minutes is None or tgt_minutes is None: return None session_open = ts.replace(hour=9, minute=15, second=0, microsecond=0) if ts < session_open: return None minutes_from_open = (ts - session_open).total_seconds() / 60 bucket_index = int(minutes_from_open // tgt_minutes) bucket_start = session_open + timedelta(minutes=bucket_index * tgt_minutes) return bucket_start + timedelta(minutes=tgt_minutes - src_minutes)

5m Recovery Preflight Matrix — Read-Only

No bulk writes performed
This section is a static analysis preflight only. It describes the root cause, the recovery approach, and the safety envelope. The actual bulk recovery has not been executed and requires your explicit approval in the next step.
Root cause
backfill_intraday_5min.py:77 — INSERT targets intraday_candles_5min, a table that was renamed to deprecated_intraday_candles_5min in the DB-09 refactor. Every run since DB-09 has silently failed with psycopg2.errors.UndefinedTable. The correct target is the canonical candles table with timeframe='5m'.
Scope of gap
All tickers that have 5m candles in the live DB. The script was a one-time bulk run on 2026-08-09 (evidenced by created_at clustering on that date). Since then, live 5m candles are only built from the AngelOne WebSocket feed for tickers with active subscriptions (≤500 via LRU). The gap is everything else from 2026-08-09 to present.
Recovery path
Fix backfill_intraday_5min.py to write to candles with timeframe='5m' using ON CONFLICT DO NOTHING, then re-run for the gap period. The batch-boundary fix must be live before any retention cycle runs on the recovered data — this is now satisfied.
Data provider
AngelOne getCandleData historical endpoint. CHUNK_DAYS=60, MAX_WORKERS=10 (ThreadPoolExecutor). Falls back to main credentials if HISTORICAL_* env vars unset. Filters weekends automatically (ts.weekday() >= 5: continue).
Rate limits
AngelOne historical API: no documented rate limit, but the existing MAX_WORKERS=10 provides natural throttling. The current implementation makes a single un-chunked getCandleData call per ticker in historical_service.py — no chunking, no retry back-off beyond the retryable flag. Recommended: keep MAX_WORKERS ≤ 5 during recovery to reduce provider-side throttling risk.
Conflict strategy
ON CONFLICT DO NOTHING — live-built candles (source LIVE, built from actual ticks via batch_flush_candles) are more accurate than OHLCV-only historical data and must never be overwritten. A historical backfill row that conflicts with an existing candle at that (ticker, timeframe, timestamp) is silently dropped.
Rollback plan
Delete all rows inserted by the recovery run: DELETE FROM candles WHERE timeframe='5m' AND is_backfilled=true AND data_source='HISTORICAL' AND created_at >= <run_start>. Idempotent: re-running the recovery after a rollback is safe because ON CONFLICT DO NOTHING skips any rows already present.
Validation plan
After recovery:
  • 5m row count in candles must be strictly greater than pre-recovery count.
  • No 5m candle timestamp should fall outside NSE session hours (09:15–15:25 IST).
  • Per-ticker session completeness: each trading day should have exactly 75 5m rows.
  • Zero candles at 15:30 slot (phantom candle check — separate P2 fix).
  • No duplicate (ticker, timeframe, timestamp) — enforced by uix_candle_key.

Section E

Recovery Safety Assessment

Batch-boundary fix safe?
YES — 89/89 tests pass
Zero regressions. All four affected chains tested (5m→15m, 5m→30m, 5m→1h, calendar chains). The fix adds ≤2 extra rows per batch iteration for the common case — negligible cost.
Live candle preservation
SAFE — ON CONFLICT DO NOTHING
Historical backfill uses DO NOTHING, not DO UPDATE. Any live-built 5m candle already in candles wins unconditionally. Historical data fills genuine gaps only.
Retention cascade risk
NONE — cutoff window protects
Retention only touches data older than the cutoff (60+ trading sessions for 5m→15m, ≈3 months). Recovered data in the recent window won't be promoted in the same cycle.
Rollback path
CLEAN — tag + delete
Recovery rows are tagged is_backfilled=true, data_source='HISTORICAL'. A single timestamped DELETE removes only recovery inserts without touching live or pre-existing historical data.
Phantom candle risk (15:30)
LOW — separate P2 fix
956 phantom 5m rows at the 15:30 slot already exist from the WebSocket path. Recovery data from AngelOne will not add new 15:30 phantoms (the provider returns session-bounded data). Existing phantoms are a separate P2 issue.
Provider availability
VERIFY BEFORE RUN
AngelOne historical endpoint has no documented SLA. Run the preflight SQL queries (Section D) first, then confirm the AngelOne token is valid before starting the bulk recovery.
Overall Safety Verdict
The prerequisite batch-boundary fix is implemented, tested, and safe. The 5m recovery is safe to proceed subject to: (1) running the preflight SQL queries from Section D to establish the baseline row count, and (2) confirming AngelOne token validity. No other blockers have been identified.
