5m Ingestion Recovery

Why universe-wide 5-minute ingestion stopped on 2026-07-03, exactly what is missing, whether it can still be recovered, and what a sustainable replacement looks like under real provider limits.

Root cause
A table rename silently decommissioned the only universe-wide intraday feed

Nothing crashed and nothing regressed. Universe-wide 5m data was produced by backfill_intraday_5min.py — a manually run script that lives outside the application and writes to intraday_candles_5min. The DB-09 refactor renamed that table to deprecated_intraday_candles_5min. The script's INSERT target no longer exists, so it can no longer run at all. Its last successful run covered through 2026-07-03.

01

The causal chain, proven

1
Universe-wide 5m came from a manual script, never from the app
backfill_intraday_5min.py: CHUNK_DAYS = 60, a ThreadPoolExecutor fan-out over all tickers, and a raw INSERT INTO intraday_candles_5min. No scheduler in the application ever invoked it.
2
The only scheduled ingestion job covers 1D, not intraday
_daily_prefill_all runs at 19:00 IST over every ticker in stock_metadata — and 1D coverage held at ~3,150 tickers/session straight through the incident. _startup_backfill is not a candidate: it takes .limit(50) tickers and its own docstring says "intraday not persisted to DB" — it only warms the yfinance cache.
3
DB-09 renamed the script's target table out from under it
The refactor renamed the legacy tables to mark them dead. That silently broke the external script, which has no test, no monitor, and no owner inside the codebase.
4
The legacy table shows the identical cliff — so it happened before the unified migration
This rules out the unified-table migration as the cause. The cliff was already present in the source.
5
The 2026-08-09 bulk copy faithfully reproduced the cliff
backfill_unified_from_legacy.py wrote 4,782,790 rows for 3,279 tickers into candles in a single run — inheriting exactly the coverage the legacy table had, cliff included.
6
Since 2026-07-06, only two writers remain
The live AngelOne websocket (~850 tickers, bounded by the 500-subscription cap with LRU rotation) and per-ticker on-demand gap-fill triggered when someone opens a chart. Both are demand-driven, so coverage tracks what users happen to view.

04

Sustainable ingestion architecture

The design constraint is not throughput — it is that ingestion must live inside the application and be observable. The failure here was not technical; it was that a critical path lived in an unowned script with no monitor. Every element below already exists in the codebase in some form.

Shape — mirror the one job that never broke

  • Scheduled in-app, not external. An _intraday_prefill_all task alongside _daily_prefill_all, running post-close (≈18:30 IST, ahead of the 19:00 daily job).
  • Universe from stock_metadata, the same source _daily_prefill_all uses — so the two feeds can never drift apart.
  • Per-ticker job rows reusing the migration_jobs pattern (status, retry_count, rows_inserted) already proven in the 1D migration, giving resumability and a queryable audit trail.
  • Idempotent, fill-only writes — ON CONFLICT DO NOTHING, never DO UPDATE (see §05).

Provider budget

Steady-state nightly run
tickers                        3,276
window per night               1 session  →  1 request each
requests                       3,276
at ~3 req/s (AngelOne cap)     ≈ 18 minutes

One-time backfill of the 31-session gap
window 31 days → 2 chunks of ≤30 days   →  2 requests each
requests                       6,552
at ~3 req/s                    ≈ 36 minutes   (single off-hours run)

Both fit comfortably in a nightly window. Throughput was never the obstacle.

Isolation — use the primitives that already exist

  • _bg_executor (4 workers, thread_name_prefix="bgjob") — never the default executor, which request handlers share via asyncio.to_thread.
  • _yf_bg_semaphore (10) for any yfinance fallback — separate from _yf_semaphore, which serves user requests.
  • Open the DB session immediately before each write, never across a provider call — the pool is 20+30 and this is the documented cause of past stalls.

Observability — the actual missing capability

A coverage check that compares distinct tickers with 5m data per session against the 1D universe would have flagged this on 2026-07-06 instead of six weeks later. That single query is the highest-leverage addition in this whole document: it is the difference between a one-day gap and a 90,139-cell hole.

05

Non-interference proof

Each claim below is grounded in a specific code path, with the residual risks stated rather than glossed.

Against live WebSocket infrastructure

Backfill never touches subscription state

The historical path contains no viewed_ticker_mgr or subscribe call. The only writer of execution ref-counts is the execution engine.

verified: grep over perform_on_demand_backfill → no WS calls · only caller of set_execution_ref_counts is execution_engine.py:74

REST fetches consume no subscription slots

getCandleData is a REST call. The 500-subscription cap and its LRU eviction govern the websocket only, so backfill cannot displace a viewed or execution-pinned ticker.

ViewedTickerManager, main.py:166 — cap applies to WS subscribe/unsubscribe exclusively

Thread and connection isolation already exists

_bg_executor and _yf_bg_semaphore are distinct from _live_executor and _yf_semaphore. Live price resolution cannot be starved by background fetching provided the background primitives are used.

main.py:340-342 (semaphores), 1219 / 1226 (executors)

Residual risk — shared AngelOne session

REST historical and the live websocket authenticate through the same AngelOne session. Un-throttled REST could trigger provider-side rate limiting that degrades the live feed. This makes throttling a live-safety requirement, not merely good manners — and it is the single strongest argument for adding the token bucket before any bulk run.

historical_service uses angelone_service.get_token(); _angel_auth_refresh shares the session

Against the retention / promotion pipeline

The gap window sits safely inside the 5m retention window

Retention only selects rows older than the cutoff, currently 2026-05-25. The recovery window starts 2026-07-06 — 28 sessions of headroom. Restored rows will not be promoted or deleted on the next cycle.

RetentionService._session_cutoff(60, now) → 2026-05-25 · retention_service.py:209,231

Retention only consumes completed candles

Both the ticker scan and the row scan filter is_completed == True. Backfilled historical rows are written completed, so they are eligible in the ordinary way — no special casing, no partial-candle hazard.

retention_service.py:209, 231

Concurrency is already guarded

Retention holds a _running flag and a lock, and processes per-ticker with keyset pagination and per-batch commits. A concurrent backfill writing different (older, missing) rows cannot deadlock against it.

retention_service.py — _running guard, per-ticker _process_ticker

Residual risk 1 — must write fill-only, never upsert

The aggregator's conflict clause does high=greatest, low=least, close=excluded, volume=excluded, guarded only by NOT (is_completed AND existing.volume > new.volume AND close ≠ new.close). A backfill reusing that path could overwrite a live-built candle with lower-quality provider data. Use ON CONFLICT DO NOTHING — then interference is structurally impossible rather than merely unlikely.

aggregator.py:683-691

Residual risk 2 — fix the batch-boundary bug first

Restoring ~6.76M rows and then letting retention promote them will run the known batch-boundary defect over the whole restored dataset, corrupting roughly one bucket per 100 source rows and deleting the evidence. The ordering matters: fix the bucketing before the restored data crosses the 60-session boundary, not after.

retention_service._process_ticker — batch_size=100 vs 3 rows per 15m bucket
