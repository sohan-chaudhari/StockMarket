§3 Phase 2B — diff methodology

Before running anything, cheap aggregate queries (COUNT/MIN/MAX, sub-100ms each) were run first to size the comparison and decide full-vs-sampled — per the instruction to report a sampling strategy only if full comparison wasn't affordable.

stock_data: 792,832 rows · 3,285 distinct tickers · dates 2015-01-01 → 2026-07-10 candles(1D): 28,721 rows · 2,643 distinct tickers · dates 2026-07-21 → 2026-08-10

Decision: full comparison, no sampling. Combined row count (~820K) and every query in this report completed in well under one second against the local Postgres instance — sampling would have traded completeness for no measurable benefit. All queries below ran against every ticker and every date in both tables.

Exact queries executed (all read-only SELECT, no db.execute call in this phase wrote, inserted, updated, or deleted anything)

SELECT COUNT(DISTINCT ticker) FROM candles WHERE timeframe='1D'; SELECT MIN(timestamp), MAX(timestamp) FROM candles WHERE timeframe='1D'; SELECT DISTINCT timeframe FROM candles; -- row-level overlap (the core diff) SELECT COUNT(*) FROM stock_data sd JOIN candles c ON c.ticker = sd.ticker AND c.timeframe = '1D' AND c.timestamp::date = sd.date; SELECT COUNT(DISTINCT sd.ticker) FROM stock_data sd JOIN candles c ON c.ticker = sd.ticker AND c.timeframe = '1D' AND c.timestamp::date = sd.date; -- ticker-set overlap WITH sd AS (SELECT DISTINCT ticker FROM stock_data), cd AS (SELECT DISTINCT ticker FROM candles WHERE timeframe='1D') SELECT (SELECT COUNT(*) FROM sd), (SELECT COUNT(*) FROM cd), (SELECT COUNT(*) FROM sd JOIN cd USING(ticker)), (SELECT COUNT(*) FROM sd LEFT JOIN cd USING(ticker) WHERE cd.ticker IS NULL), (SELECT COUNT(*) FROM cd LEFT JOIN sd USING(ticker) WHERE sd.ticker IS NULL); §4 Coverage findings — the headline result

The two tables currently have zero overlapping (ticker, date) rows. stock_data's most recent date is 2026-07-10; candles(1D)'s earliest date is 2026-07-21. A direct join on (ticker, date) returns 0 matching rows across the entire dataset. This is VERIFIED by direct query, not inferred.

This changes what "diff" means in practice today: there is no shared ground truth to compare OHLC/volume values against row-by-row, because the two tables cover disjoint time periods, not the same period from two sources. The sections below report what can be determined given that.

Confirming that fallback is actually firing in practice is outside what a read-only DB query can determine.

§6 Timestamp convention — confirmed with real data, not just code

Confirmed100% of candles(1D) rows are stored at midnight (00:00:00)V

All 28,721 rows return timestamp::time = 00:00:00 — no exceptions. This validates, with live data rather than just code-reading, the earlier finding that 1D candles break the 09:15-IST-session-anchoring convention every other timeframe in the same table follows.

stock_data.date is a plain DATE column — no time component exists to compare, which is itself the third, structurally different convention flagged previously.

Practical impact: because there is currently no overlapping data (§4), this inconsistency has not yet caused an observable wrong-answer for any user — but it becomes load-bearing the moment any consolidation or resampling logic needs to align a 1D candle's timestamp with the 09:15-anchored intraday tiers it's nominally derived from (e.g. computing a session boundary, or joining 1D against 4h/1h data for validation). Any future cutover must explicitly decide and normalize this, not inherit it silently.

V adj_close is far sparser than the earlier code-only analysis characterized it — it isn't just "unreliable on some write paths," it's absent entirely on over 90% of rows. Only a small, inconsistent slice of the table's history has a populated, genuinely-adjusted value at all. candles(1D) has no adj_close column, so this comparison has nothing to be checked against there.

A real, detectable corporate-action signature

The largest divergences all belong to a single ticker, VEDL, across many different 2015 dates, each showing an almost identical ~68.32% gap between close and adj_close (e.g. close 173.20 vs adj_close 54.86 on 2015-06-18; close 212.40 vs adj_close 67.28 on 2015-05-04 and again on 2015-03-04). V 2,817 of VEDL's rows carry a non-null adj_close. The near-constant ratio across unrelated dates is the signature of a single retroactive adjustment factor applied by yfinance across VEDL's pre-event history — consistent with a real corporate action, though this analysis does not assert which specific event, since that would require external verification beyond what the stored data alone proves.

Why this matters for Decision 1: a consolidation onto candles as canonical would currently mean losing whatever genuine adjustment signal exists in that 9.2% slice of stock_data, since candles has no adjusted-price concept at all today. That's a real (if narrow) capability regression to weigh, not just a schema simplification.

§8 Other discrepancies found

  • V candles(1D) has a data gap of its own: 2026-07-22 is missing entirely (dates jump from 07-21 straight to 07-23), and 07-23 itself only has 1,005 tickers versus ~2,600 on every surrounding day — a partial day. Whether 07-22 was a legitimate market holiday or a job failure was not determined by this analysis (would need the holidays/market_sessions tables cross-referenced, out of this phase's scope).
  • V candles(1D) is 100% data_source='YFINANCE' — despite historical_service.py supporting an Angel One REST path for daily data in principle, nothing in the current 1D data actually came from it.
  • Inferred — stock_data's 647 exclusive tickers (present there but not in candles) are plausibly delisted, renamed, or otherwise-inactive symbols that predate the current active-ticker universe the newer background jobs iterate over — this wasn't cross-checked against stock_metadata.is_active in this pass and should be confirmed before any cutover, since silently dropping 647 tickers' history would be a real regression for anyone who navigates to one of them.

§10 Recommended next phase and open decisions

Per the safety rule, Phase 2 ends here. No consolidation, cutover, or migration work is proposed or started. The most useful next step this diff points to is not "pick a winner and migrate" — it's resolving the specific unknowns this diff surfaced, since several of them change what a safe migration would even look like:

  1. Confirm whether the 647 stock_data-only tickers are inactive/delisted (check against stock_metadata.is_active) — determines whether a candles-only future loses real, still-relevant history.
  2. Decide how (or whether) to preserve the 9.2% adjusted-price signal currently only in stock_data.adj_close — candles has no field for it today.
  3. Decide the 1D timestamp convention explicitly (adopt 09:15-anchoring for consistency, or formally accept midnight-anchoring as 1D's own convention) rather than let it stay an unexamined inconsistency.
  4. Investigate the 2026-07-22/23 gap/partial-day in candles(1D) — holiday or job failure — before trusting that pipeline as a sole source going forward.

Whether to proceed to a "resolve the unknowns" sub-phase covering the four items above, before any cutover-planning phase begins. This report does not assume yes.
