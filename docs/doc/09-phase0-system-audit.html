04

External dependencies

  • Angel One SmartAPI — one account serves both the live WS/REST feed (angelone_service.py) and, by credential fallback, historical fetches (historical_service.py). This sharing is the root of RT-01.
  • SmartWebSocketV2 SDK (vendor, bundled) — internal reconnect/blocking behavior partially unverified; treated as a black box.
  • yfinance — legacy daily source, plus a still-active daily-close backfill and pre-warm job pair.
  • Postgres — primary datastore, single instance, no read replica found.
  • Sentry — error tracking, imported at main.py top.
  • No Redis, no message broker, no distributed lock — see §05 note on single-process design.
Architecture constraint. Every service singleton (angelone_service, aggregator, viewed_ticker_mgr, execution engine) is a plain module-level Python object with in-process locks. No Dockerfile/Procfile/uvicorn-workers config was found — consistent with a single-process deployment. If ever scaled to multiple workers, most of this breaks (duplicate AngelOne logins, duplicate aggregators); order double-execution specifically stays safe due to DB row locks.
05

Findings register

47 items, deduplicated across four independent passes — the WebSocket subscription-cap DoS (RT-03) was found twice, independently, from different code paths, which is why it's marked as strongly verified rather than single-source. Every item cites the file:line evidence it rests on.

Criticalfix before anything else touches this code
Dual Angel One session collision can kill the live feed for every userRT-01

HISTORICAL_API_KEY/CLIENT_ID/PASSWORD/TOTP_TOKEN are empty in .env, so historical_service.py silently falls back to the same credentials angelone_service.py uses for the live feed. A second, independent generateSession() call — triggered just by a user viewing a not-yet-recovered ticker — can invalidate the live session platform-wide on brokers that revoke the prior token on new login (common AngelOne behavior).

.env: HISTORICAL_* empty · historical_service.py:92-98 fallback · triggered via recovery_service.py:110-112, main.py:753-755, main.py:2940-2942
Recommendation

Provision genuinely separate credentials for historical fetches, or route through the same session singleton as the live feed.

Session failures are invisible for up to 12 hoursRT-02

is_logged_in only flips false on an explicit "token missing" error from one call path. The REST pollers swallow every other failure and just return False without touching it — so a session killed by RT-01 (or anything else) produces silent zero-data with no self-healing until the 12h proactive-refresh timer.

angelone_service.py:620,645 (only write sites) · price_poller.py:127-189, 249-329 (never write it)
Recommendation

Feed poller failures back into the health flag — e.g. force re-login after N consecutive ltpData failures.

Unauthenticated WS endpoint allows a full subscription-cap DoSRT-03

/ws/dashboard requires no auth (by design — it's public market data) but accepts an arbitrary, unvalidated ticker string in view_ticker and immediately consumes a real slot against the 2,000-subscription cap before ever checking the ticker resolves to anything. One connection sending 2,000 garbage names exhausts the cap and cuts live prices for every real user. Confirmed independently by two separate discovery passes tracing from opposite ends of the call chain.

main.py:2350-2392 (no auth) · main.py:2377 (no ticker validation) · main.py:161-197 ViewedTickerManager.view()/_try_subscribe · main.py:4068 max_subscriptions=2000
Recommendation

Validate ticker against the known instrument set before counting it against the cap; rate-limit inbound WS messages per connection.

/ws/user pins a pooled DB connection for its entire lifetime — hard ~30 concurrent user ceilingDB-01

FastAPI resolves Depends(get_db) at WS-accept time and only closes it on disconnect. The handler uses the session once for auth, then sits in a receive loop for the rest of the connection — holding one of only 30 pooled connections idle the whole time. This caps concurrent logged-in users at ~30 regardless of hardware, on a platform meant to be left open during market hours.

main.py:961 Depends(get_db) on WS route · database.py:38-44 pool_size=10 + max_overflow=20
Recommendation

Open a short-lived SessionLocal() for the auth check only; don't inject the pooled dependency into a WebSocket route. The correct pattern already exists elsewhere in the file (main.py:4788).

Drawing anchors silently go wrong after any history-scroll loadFE-01

window._chartCandles is the documented single source of truth for drawing-anchor math — array index is treated as chart logical index. It's correctly synced on initial load and WS-reconnect, but the infinite-scroll pagination path updates the visible chart series without ever updating this array. Since the whole array shifts on a history load, every existing drawing's recomputed anchor becomes wrong, not just new ones.

dashboard.js:1619-1671 _fetchMoreData (missing assignment) vs correct pattern at :1696-1697, :1949-1950 · contract documented at drawing-core.js:242-245
Recommendation

Add window._chartCandles = combined; in _fetchMoreData immediately after _chartDataCache is set.

Closed-positions tab is always empty, silentlyFE-02

The trading panel's "Closed" tab expects {positions: [...]}; the backend returns a bare array. A different call site in the same file, and portfolio.html, both handle the real shape correctly — this one spot was simply missed. Currently shipping, not hypothetical.

stock-logic.js:686-699 expects {positions:[...]} · main.py:1022-1067 returns a bare list · duplicate dead route at main.py:2740-2774 also returns bare list
Recommendation

Fix the one call site to read the array directly, matching the other two working call sites. Also remove the dead duplicate route.

Highreal reliability/security gaps, none catastrophic alone
LiveTimeframeManager never releases a viewer — permanent degradation once the 5,000-builder cap is hitRT-04

remove_viewer exists but has zero call sites anywhere outside its own definition and unit tests. Every 15m/30m/1h request adds a viewer that's never removed; once 5,000 distinct (ticker, timeframe) combinations have ever been requested, every new one permanently falls back to the slow DB/resample path — recoverable only by restart.

live_timeframe_manager.py (definition only) · main.py:3345-3348 add_viewer, no balancing call anywhere
Chart close doesn't reliably unsubscribeRT-03b

The frontend resends its entire ticker list (not just the delta) on every chart open/switch; the backend calls .view() unconditionally for all of them. Disconnect cleanup only decrements once per ticker. Net effect: subscriptions creep toward the cap over a trading day and essentially never shrink for actively-viewed tickers.

frontend/ws.js addTickers() resends full list · main.py:2361-2367 no diff before view() · main.py:2384-2392 unview_all decrements once
Reconnects under 120s at a candle boundary produce a silently wrong candleRT-05

A disconnect/reconnect spanning a 5m boundary finalizes the forming candle with whatever ticks it had before the gap — no backfill triggers below the 120s staleness threshold. Worse, RecoveryService only ever recovers a given ticker once per process lifetime; the second gap for the same ticker that day is never fixed.

aggregator.py:295-353 finalize on boundary · main.py:4417-4426 >120s gate · recovery_service.py:35-43 one-shot set
The purpose-built fix for RT-05 already exists and is dead codeRT-06

GapRecoveryService.recover_5m_gaps() is fully implemented for exactly the repeated mid-session gap case (cooldown-based, >600s trigger, REST backfill + merge) — and has zero call sites anywhere in the running app.

gap_recovery.py:18-113 · exhaustive grep confirms no caller outside its own file and a historical audit doc
Old Angel One WebSocket is never closed on a proactive re-loginRT-07

Every 12h relogin overwrites self.sws with a fresh socket but only join()s the old thread — it never calls close() on that path. Over time this can leave duplicate live sockets running, doubling AngelOne connection usage per account.

angelone_service.py:146-205 (no close on this path) · close() only called at :248, a different branch
Blocking I/O stalls the shared event loopRT-08

The 30-minute auth-refresh task and the startup subscription handshake both perform synchronous blocking calls (the handshake waits up to 15s) directly on the asyncio loop. For the duration, every concurrent HTTP request and WebSocket broadcast stalls platform-wide.

angelone_service.py:207-220 ensure_connection() not threaded · subscribe_tickers() time.sleep(0.5) loop, angelone_service.py:393-430
Rate limiting was removed from every sensitive endpoint except oneSEC-01

slowapi is wired up but applied to exactly one route. Register, forgot-password, resend-verification, login, and both trade-open/close endpoints have zero rate limiting. A leftover backup file shows these previously had @limiter.limit(...) decorators — a real regression, not a gap that was never filled.

main.py:425-426, 1470 (only decorated route) · auth_router.py, trade_router.py (zero decorators) · main_recovered.py:1578,1623 (prior protection)
Aggregator's DB-flush queue has no size capRT-09

Under a sustained Postgres outage, completed-candle batches accumulate in an unbounded in-memory list with no ceiling — directly contradicting the module's own docstring claim that ticks are "never dropped" via backpressure. In practice there is no pause; the queue just grows.

aggregator.py:196-200 unbounded list · docstring claim at aggregator.py:11 · drop-after-3-retries at :526-529
No Alembic — schema changes run unversioned, in-process, on every bootDB-02

Schema changes are hand-rolled ALTER TABLE ... ADD COLUMN IF NOT EXISTS / CREATE INDEX IF NOT EXISTS blocks inside the FastAPI startup hook, re-checked on every restart with no version tracking. One of them builds a non-CONCURRENTLY index against the 13.6M-row candles table — a first run against a populated table takes an exclusive lock for the full build, and a killed-mid-build index can silently stay invalid forever since "IF NOT EXISTS" treats an invalid index as already existing.

main.py:4064-4217 ("Migration v005/v006/v007" in comments) · CREATE INDEX at main.py:4198-4217
Triple-redundant indexes on the busiest tablesDB-03

candles, current_day_candle, and stock_data each carry a unique constraint plus two additional btree indexes on the same leading columns — one declared in the model, one injected at every startup. At 13.6M+ rows this roughly triples write cost on the table every live write path touches continuously.

models.py:127-128 (constraint + duplicate index) · main.py:4203-4206 (third index, startup-injected)
The drawing-tools audit was verified on a page users can't reachFE-03

chart.html — the page the earlier drawing-tools fix pass was tested against — has zero internal links anywhere in the app. stock.html is the real production entry point. Wiring is structurally identical (same element IDs, same script load order), so the fixes very likely transfer, but this was never live-verified on the actual page.

exhaustive grep for chart.html references → zero matches · stock.html linked from 8+ files
TP/SL can fire against a stale priceTP-01

Only tier 1 (live tick) of the 4-tier price-resolution pipeline enforces a staleness check (30s max age). Tiers 2–3 (forming/completed 5m candle) apply none — if both the WS and REST poller die simultaneously, an hour-old candle can still be returned as "current price" and used to trigger an execution.

price_provider.py:106-140 (tier 1, has check) vs :142-212 (tiers 2-3, no check)

Verified soundconfirmed correct — no action needed
  • Execution pinning for TP/SL orders (ADR-011) — DB-authoritative, immune to LRU eviction, covered by a dedicated test.
  • Duplicate-subscription prevention — one upstream Angel One subscription per ticker regardless of viewer count, no race found.
  • Angel One reconnect correctly resubscribes every previously-held token.
  • Downstream broadcast backpressure — drops for a slow client rather than queuing, bounding memory correctly.
  • Retention's insert→verify→delete→commit ordering is genuinely atomic and rollback-safe — no premature-delete risk.
  • Migration crash-recovery — the real resume path rescans actual table coverage and every write is idempotent; safe to re-run after a crash despite the job-status state machine having gaps that don't actually matter in practice.
  • Both frontend WebSocket clients implement proper exponential backoff with jitter, plus a visibility-change reconnect.
  • The primary chart timeframe-switch path has solid double-layered race protection (AbortController + monotonic load-id check).
  • Stuck-order recovery on restart carefully reconciles EXECUTING orders against actual position state.
  • /ws/user is properly authenticated and push-only — it cannot be used to mutate account state even if compromised.
