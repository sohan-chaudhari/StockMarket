Final P0 — 5m Ingestion Root Cause

P0 Fix Now
DEADLINE: Retention correctly promotes whatever exists. The 2026-07-06 holes cross the 60-session boundary (~Oct 2026), after which 5m rows are permanently deleted and gaps become irrecoverable. Recovery must happen before then.
Proven Root Cause

Universe-wide historical 5m backfill targeted the deprecated table, not the canonical store.

backfill_intraday_5min.py:77 writes: INSERT INTO intraday_candles_5min (...). That table was renamed to deprecated_intraday_candles_5min in the DB-09 refactor. The script was never updated. Every execution since the rename has silently produced a "relation does not exist" error.

The bulk BACKFILL run on 2026-08-09 (confirmed from created_at column) copied ~7.2M rows into deprecated_intraday_candles_5min, not into candles. Live WebSocket coverage (~500 subs, LRU eviction) continued into candles correctly, which is why ~850 tickers still have recent 5m data.

Hidden dependencies on deprecated table

backfill_intraday_5min.py:10: imports IntradayCandle5Min (mapped to deprecated_intraday_candles_5min). No other active application code reads or writes the deprecated tables. The deprecated_ tables are safe to ignore but must not be dropped while they still hold historical data (7.2M rows in 5min, data present).

Live WebSocket isolation — proven no interference

The live WS path writes via batch_flush_candles() → ON CONFLICT DO UPDATE on uix_candle_key. The recovery path will use ON CONFLICT DO NOTHING. These two conflict strategies on the same unique key are safe: the live-built candle wins by definition because it already exists in the table before the backfill row arrives.

The retention service runs in a separate thread, processes only is_completed=True rows older than the session cutoff, and never touches the live window. There is no shared lock or state between ingestion recovery and the live WS pipeline beyond the DB uniqueness constraint itself.

1h Coverage Collapse — Classification

P1 · Downstream Effect
Root cause: downstream of 5m collapse

1h candles in candles are produced exclusively by retention promotion: 30m → 1h (after 180 sessions). 30m rows are themselves produced by 15m → 30m (after 120 sessions), and 15m by 5m → 15m (after 60 sessions).

Since the 5m universe collapsed 2026-07-06, no new 5m rows have been added for ~3,100 tickers. The promotion chain is starved at the source. 1h collapse is not an independent bug — it is expected downstream starvation.

Evidence: 1h coverage collapsed ~1 week after 5m (2026-07-13 vs 2026-07-06). The ~7-session lag is roughly the time needed for any late-arriving 5m rows (via live WS) to reach the 30m tier. Once the 5m feed for a ticker stopped, the 30m→1h promotion had nothing new to promote.

Classification

Expected Retention Behaviour (caused by P0). Fix the 5m ingestion (Phase 0) and recovery (Phase 0), and 1h will self-heal as retention runs its promotion cycle once the restored 5m rows cross each session threshold. No separate 1h fix required.

The /api/stock-data/intraday/paginated on-the-fly resampling fallback (main.py:3759) provides a stopgap for users requesting 15m/30m/1h during the gap — it reads 5m from DB and resamples live. This is already deployed and working.

4h Alignment — Mathematical Verification

P1 · Latent Bug
The offset calculation

NSE session opens at 09:15 IST = 555 minutes from midnight. For pandas resample(rule, offset=X), the offset shifts the bucket grid from the epoch anchor so that 09:15 falls exactly on a bucket boundary.

TimeframeBucket (minutes)555 mod bucketCorrect offsetCode offsetStatus
15m15555 % 15 = 0None neededNoneCORRECT
30m30555 % 30 = 1515min15minCORRECT
1h60555 % 60 = 1515min15minCORRECT
4h240555 % 240 = 7575min15minBUG — wrong offset
Effect of wrong 4h offset

With offset='15min', pandas anchors the 4h grid at 00:15, 04:15, 08:15, 12:15, 16:15... The NSE session's 09:15 data falls into the 08:15 bucket (covers 08:15–12:15), and the second bucket starts at 12:15 (covers 12:15–16:15). Both buckets span pre/post-market hours and are misaligned with actual NSE trading.

With offset='75min' (correct), the grid anchors at 01:15, 05:15, 09:15, 13:15... The NSE session's 09:15 data begins precisely at the 09:15 bucket boundary, matching TradingView-like alignment.

Currently latent. The /api/stock-data/intraday/paginated endpoint explicitly rejects interval=4h at line 3685, and there are 0 rows in candles WHERE timeframe='4h'. No user is affected today. Fix this as part of Phase 2 (4h enablement) before enabling the endpoint.
Everything else about 4h resampling — verified correct

closed='left', label='left' is correct for OHLCV aggregation. The OHLC aggregation functions (first/max/min/last/sum) are correct. The bug is isolated to the offset value only. The fix is a single string change: '15min' → '75min' for the 4h branch in resampler.py:_resample_by_rule.

_resample_to_1w uses 'W-MON' (Monday-anchored) — verified correct for NSE which counts weeks Monday–Friday. _resample_to_1m uses 'MS' (month start) — verified correct.

15:30 Phantom Candles — 76-Candle Sessions

P1 · Data Pollution
Mathematical analysis of snap_to_nse_session

Constants from aggregator.py:27-35:

NSE_OPEN  = 09:15 → _NSE_OPEN_SEC  = 33300
NSE_CLOSE = 15:30 → _NSE_CLOSE_SEC = 55800
NSE_GRACE = 15:45 → _NSE_CLOSE_GRACE_SEC = 56700

bucket_sec = 5 * 60 = 300
slots = (55800 - 33300) // 300 = 22500 // 300 = 75

Branch logic at lines 78–84: for ist_seconds ∈ [55800, 56700) (i.e., 15:30:00 – 15:44:59), the code enters the elif ist_seconds >= cl: branch, computes slots=75, and returns session_start + 75 × 300 = session_start + 22500s, which is exactly 15:30 IST.

The correct last bucket is 15:25 (the 75th slot, 0-indexed as slot #74, starting at session_start + 74×300 = 15:25). Any tick arriving at or after 15:30 should either go to 15:25 (if the candle is still forming) or be discarded — not open a new 15:30 bucket.

Evidence and scope
Phantom rows956 rows in candles WHERE timeframe='5m' AND EXTRACT(hour from timestamp)=15 AND EXTRACT(minute from timestamp)=30 13 rowsSame query on timeframe='15m' (promoted from phantom 5m rows) Affected sessionsSessions with 76 5m candles instead of 75 (2 RELIANCE sessions confirmed; likely broader) ClassificationData Pollution: the 76th candle is real price data but misattributed to an invalid time slot. It corrupts the session's OHLC when the chart stitches candles together.
Fix design (do not implement yet)

Step 1 — Data cleanup: Delete or merge the 956 phantom 5m rows and 13 phantom 15m rows. If a 15:25 candle already exists for the same ticker/date, merge (using GREATEST/LEAST for high/low, keep the 15:25 open, take whichever close is later in real time). If no 15:25 exists, update the phantom's timestamp to 15:25.

Step 2 — Code fix: In snap_to_nse_session, change the elif ist_seconds >= cl branch. Ticks at or after 15:30 should return the 15:25 bucket (session_start + (slots-1) × bucket_sec, same logic as the if ist_seconds >= cg branch). The grace-period logic (15:30–15:44 is "within trading" for WS purposes) is correct for accepting the tick — the error is only in where the tick gets bucketed.

Retention Checksum Gate

P2 · Integrity Gap
Retention batch-boundary corruption — verified with example

_process_ticker in retention_service.py:218 fetches batch_size=200 source rows per iteration, resamples them, verifies the batch's checksum, inserts targets, deletes sources, commits. The bug: a 15m candle needs exactly 3 source 5m rows. If a batch boundary splits those 3 rows (e.g. 2 in batch N, 1 in batch N+1), batch N produces an incomplete 15m candle using only 2 of the 3 required 5m rows.

When batch N+1 arrives, the incomplete 15m candle already exists due to ON CONFLICT DO NOTHING — the correct aggregate is blocked. The result is a 15m candle with wrong OHLC (high underreported, volume underreported).

Reproduced example: high 206→204, close 202→200, volume 30→10.

Checksum does not catch this

The _verify_checksum method (retention_service.py:350) compares source vs. target within the same batch: source["volume_sum"] == target["volume_sum"]. Since the partial 15m target's volume (10) matches the partial batch's source volume (10 for the 2 included rows), the checksum passes. The corruption is invisible to the gate.

migration_jobs checksum state — separate issue

3,044 of 3,277 rows in migration_jobs have checksum_src != checksum_db including rows with status='DONE'. The migration checksum gate is not enforced on state transition — a row reaches DONE regardless of checksum comparison. 4 rows are stuck FETCHING since 2026-08-14 with retry_count=0 and no recovery sweep.

Classification: P2 — the 1D migration is a one-time operation, now largely complete. The checksum mismatch indicates the gate was never enforced, not that the data itself is wrong (the 1D candles from _daily_prefill_all are correct). Stuck FETCHING rows need a timeout-based recovery sweep, not a data fix.

Fix design for batch-boundary bug

Before resampling, extend the batch to include all source rows that belong to the same target bucket as the last source row in the batch. For 5m→15m: the last timestamp in the batch rounded down to the 15m boundary — include all 5m rows up to (that boundary + 15min) in the same batch. This prevents a 15m bucket from ever being split across two batch fetches.

Alternative: change ON CONFLICT DO NOTHING → DO UPDATE using GREATEST/LEAST for high/low and + for volume on target inserts, so a second batch can complete an existing partial candle. This is simpler but requires proving that the second batch always contains the same or later timestamp data.

5.1% Close Disagreement — Source-of-Truth Policy

Evidence
Overlapping rows728,853 date-ticker pairs present in both stock_data and candles/1D Disagreeing rows37,530 — 5.1% differ on close price Write frequencycandles/1D: 800–2,600 inserts/day (scheduled yfinance). stock_data: ~2/day (on-demand fallback)
Likely causes
  • Corporate actions (dividend/split): yfinance returns adjusted prices when auto_adjust=True (the default). If _daily_prefill_all and the on-demand fallback use different auto_adjust settings, or if one path fetches on ex-dividend date and another after adjustment, close values diverge. This accounts for the majority of the 5.1%.
  • Provider timing: yfinance prices a session using end-of-day data; if fetched intraday (during market hours) vs. post-market, the "final close" vs. the "last known price" differ.
  • Rounding: Minor float precision differences between two yfinance calls for the same ticker/date.
Source-of-truth policy — to be made explicit

candles/1D is the operational source of truth for display prices (open/high/low/close). It is updated daily by a scheduled job and is always fresher than stock_data. The ON CONFLICT DO UPDATE SET high=GREATEST, low=LEAST, close=EXCLUDED.close in _daily_prefill_all means the most recent fetch wins.

stock_data is the authoritative source for adj_close only. Once the adj_close column is added to candles and backfilled, stock_data's OHLC role becomes redundant.

Do not silently pick one: document this policy in a comment in _daily_prefill_all and in the API response for /range/paginated.
