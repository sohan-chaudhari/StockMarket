§3 Candidate B — Historical Data Consolidation (read-only diff stage only)

High impactWide scope

stock_data vs candles

Graph position
Sits directly in the path every user's daily/weekly/monthly chart takes, and directly upstream of any future Recommendation Intelligence training pipeline — the highest-traffic, most consequential node of the three candidates.
Business impact
High. V Confirmed: daily reads (/api/stock-data/range, price_provider.py tier 4, chart_service.py's daily branch) are hard-wired to stock_data; weekly/monthly and the health/monitoring endpoint (/api/candle-health) are hard-wired to candles. This is a real architectural split affecting what users see every day, not just latent duplication.
Data-integrity impact
High, and worse than previously characterized. Three new, verified facts this pass surfaced:
  1. V 1D timestamp convention differs from the rest of the app. candles rows for every other timeframe are 09:15-IST-session-anchored; 1D rows are stored at midnight (resampler.py:69 explicitly excludes '1D' from the 09:15-offset logic; the daily background sync jobs insert yfinance's midnight-indexed timestamps as-is). stock_data.date is a plain Date column with no time component at all — a third convention.
  2. V adj_close is only a genuine adjusted price on stock_data's yfinance-sourced rows — the AngelOne-fallback and candles-fallback write paths just copy raw close into adj_close. It is not reliably meaningful today.
  3. V No 4h→1D retention downgrade exists. retention_service.py:14 explicitly documents daily/weekly as handled separately — this contradicts what the earlier Decision 1 analysis left as an open question ("may also write candles(1D) over time... not conclusively ruled out"). It's now resolved: retention does not feed candles' 1D tier at all. All 1D rows in candles come from three independent yfinance-based jobs (backfill_daily.py, the "DailySync" and "DailyPreFill" background jobs in main.py).
Dependency impact
Directly gates the approved Decision 1 target ("candles becomes canonical"). Also — this is new — the shared Candle contract already handed to future Team 1/Team 2 promises IST-naive, 09:15-session-anchored timestamps (Decision Package §Shared Contracts). The 1D convention violates that promise today. Any Recommendation Intelligence work consuming daily candles inherits this inconsistency unless it's resolved first.
Risk (this stage only — read-only diff)
Very low. No writes, no schema change, no production code path touched.
Reversibility
The diff/analysis stage is trivially reversible (it changes nothing). Later stages (comparison → mismatch investigation → cutover) each need their own approval gate per Decision 1's already-approved phased process — this report does not propose skipping any of them.
Scope
Wide for the eventual full consolidation (historical_service.py, backfill_daily.py, the two daily background jobs, chart_service.py, price_provider.py). Narrow for this stage: one new read-only comparison, no production path changes.
Testing difficulty
Straightforward for the diff itself (row-by-row comparison, mismatch report). NOT VERIFIED whether the two tables' values actually differ in practice — that specifically requires live DB access this analysis pass didn't perform, which is exactly what the diff stage exists to produce.
Production risk
None for the diff stage.
Team dependency
Diff/analysis stage: Core-only. Per Decision 1's original owner note, Team 2 (Recommendation Intelligence) should be briefed before any actual cutover — not required for this stage.
Blocking potential
High. Blocks trustworthy AI/ML readiness work and leaves an already-published contract promise (09:15-anchored Candle timestamps) inconsistent with real data.
Existing tool found, not built this pass: count_active_tickers.py (backend root) already prints per-table ticker counts and date ranges for both tables, with comments "(Legacy Table)" / "(Future Storage)" — evidence the migration intent was anticipated by a prior author. Worth running manually before the diff-stage script is built, as a fast sanity check.

§5 Other issues found this pass

Correction to a previous report: the Decision 1 analysis (prior session) left open whether retention_service.py's downsample pipeline might also populate candles' 1D tier over time. Anything reading adj_close expecting a genuine split/dividend-adjusted price should not trust it universally. Relevant context for Candidate B, not a new standalone issue.
  • V price_provider.py's tier-4 fallback (used outside market hours) is a load-bearing, code-level dependency on stock_data specifically — any Candidate B cutover must update this, not just the obvious chart-facing endpoints.

§10 Proposed Phase 2

Scope

Candidate A in full (chart_service.py timeframe-case fix + bounded query on /api/stock-data/chart), plus Candidate B's read-only diff/analysis stage only (compare stock_data and candles(1D) per ticker, report mismatches beyond a defined tolerance, quantify how much the 1D-anchor and adj_close issues actually affect stored values).

Goals

  • Close the last known correctness gap in chart_service.py before it becomes load-bearing.
  • Produce a concrete, evidence-based answer to "do the two daily tables actually disagree, and by how much" — currently NOT VERIFIED without live data.
  • Quantify the practical impact of the 1D-anchor and adj_close inconsistencies discovered this pass.

Non-goals

  • No cutover of any read path to a new canonical daily source.
  • No schema changes, no data writes, no table deletion.
  • No work on Candidate C.
  • No reinterpretation of Decision 2 (canonical resolution stays frozen).
  • No Options/Recommendation Intelligence code.

Entry criteria

  • This report approved.
  • Explicit go-ahead to query production data for the diff stage (Human Decision #2 above).

Exit criteria

  • chart_service.py case bug fixed and tested; unbounded query bounded and tested; full backend suite green.
  • A diff report exists showing, per ticker, whether stock_data and candles(1D) values agree, and characterizing any systematic pattern in disagreements (e.g. around known split/dividend dates).
  • No production write path changed.

Expected tests

  • Unit tests for the case fix and query bound (already scoped in the approved decision package).
  • The diff itself is a report, not a pass/fail test — its "test" is human review of the mismatch findings before any cutover decision is made in a future phase.
